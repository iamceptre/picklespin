# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Picklespin is a first-person arena spell-caster game built in **Unity 6000.3.20f1** on the **Built-in Render Pipeline** (forward). The repo root contains two projects:

- `Picklespin/` — the Unity project (open this folder in Unity Editor)
- `Picklespin-FMOD/` — the FMOD Studio audio project (`Picklespin.fspro`); built banks land in `Picklespin/Assets/FMODBanks/`

There are no CLI build scripts, tests, or linters — building and playing happens through the Unity Editor. Scenes: `Assets/Scenes/Menu_Main.unity` and `Assets/Scenes/Church_Arena.unity`.

**Don't compile-test after changing code.** No `dotnet build`, no CLI compile check.

## Architecture

All game code lives in `Assets/Scripts/`

Keep new scripts in a matching folders — no loose scripts at the top level, and none outside `Assets/Scripts/` (`Assets/Editor/` and the generated `Assets/InputSystem/PlayerInputActions.cs` are the exceptions Unity requires). One MonoBehaviour per file, and **the file name must match the class name** or Unity cannot bind the component. Third-party code is in `Assets/Plugins/`: A* Pathfinding Project (enemy navigation), FMOD, DOTween (Demigiant), BeautifulDissolves, VolumetricFog, Camera Shake, Magic Light Probes.

**Rendering: Built-in RP, not URP.** 

**φ-based tuning, where it earns its place.** `Assets/Scripts/Misc/PhiMath.cs` holds the golden-ratio constants. Prefer `GoldenSequence`/`GoldenSpiralPoint` over `Random` wherever clumping or streaking would show (spawn scatter, spawn-point picks, per-instance tick offsets), and leave `PlayerMovement`'s velocity tuning φ-coherent — those constants are deliberate, not magic numbers to be flattened into literals. Plain readable numbers everywhere else.

**Singleton pattern everywhere.** scripts expose `public static X instance` (or `Instance`), assigned in `Awake()`. Cross-references to other singletons are grabbed in `Start()` — keep that ordering (never read another singleton's `instance` in `Awake()`).

**Enemy AI** (`Scripts/AI/States/`): a component-based FSM. `State` is the base; concrete states (`WaypointsForSpawner`, `AttackPlayer`, `LoosingPlayer`) are MonoBehaviours on the enemy. `StateManager` ticks the machine via `InvokeRepeating` at ~0.2s with a random per-enemy offset (deliberate perf staggering — updates are not per-frame) and calls `AiVision.PerceptionCheck()` each tick. A static `StateManager.AllManagers` list supports global queries like `IsAnyAIInAttackOrLoosing()`. Each enemy prefab has an `AiReferences` hub component aggregating its parts (health, vision, states, FMOD emitters) with `ResetAll()` used when the pooled enemy respawns.

**Object pooling, not Instantiate/Destroy**: enemies (`GameFlow/EnemiesSpawner`) and spell projectiles (`Items/PoolSpawnableObject`, `Player/Attack/SpellProjectileSpawner`) are pooled and reset via `OnEnable`/explicit Reset methods. New spawned things should follow this pattern. Nothing should be spawned or destroyed on runtime unless explicitly stated.

**Game flow**: `RoundSystem` (singleton) runs a timer and fires a serialized `UnityEvent[]` — one entry per round — plus `LastRoundEvent`. Much of the game's wiring in general goes through Inspector-assigned UnityEvents, so behavior is often not visible in code; check the scene/prefab serialized fields before concluding something is unused.

**Leaving a scene goes through `SceneFlow` (`GameFlow/SceneFlow.cs`) and nowhere else** — never call `SceneManager.LoadScene`/`LoadSceneAsync` or `Application.Quit` directly. `Load`, `Reload`, `LoadAsync` and `Quit` all pass through one door that sets `Time.timeScale` back to 1, calls `DOTween.KillAll()` and silences FMOD *before* the load — a tween or a still-playing bus that outlives the scene is where restart bugs come from — and `SceneFlow.IsLeaving` is true from that moment until the next scene reports loaded. The silencing is the static `AudioTransition` (`Audio/AudioTransition.cs`), which mutes and stops the diagetic bus and then **flushes FMOD's command queue**; don't drop that flush, because those commands otherwise run on FMOD's next update — after the incoming scene's emitters have started, which killed audio at random on restart. On arrival, a scene with an `FMODResetManager` holds the bus at silence and fades it up itself; a scene without one (the main menu) gets `AudioTransition.Restore()` from `SceneFlow` instead, so neither can start deaf.

**Every screen is a `MenuScreen`** (`Menus/MenuScreen.cs`) — one component per page, on the page's own Canvas, fading a `CanvasGroup` on **unscaled** time so the same component works in the main menu and in a pause menu at `timeScale 0`. The death, win and portal-closed screens included: never show a screen by switching its GameObject on from outside, by poking `Canvas.enabled`, or by giving it a fade component of its own — `Death`, `Win` and `PortalAfterClosing` resolve theirs through `MenuScreen.Of` in `Awake` and then call `Open()` / `SetOpen(true, onDone)` (the portal-fail blackout chains off that callback). `MenuScreen.Of` takes a Canvas or a GameObject, returns the page it belongs to, and *makes* one — `Canvas` and `CanvasGroup` included — if it has never been a page, so nothing needs page wiring of its own, the pause menu and `MoveToAnotherCanvas` (the button that steps from one page to the next) included. **A page's GameObject stays active for the whole run** — activation is not how a screen is shown, its `Canvas` is, and a page takes its state from how that Canvas was left: enabled means open. So anything living on a page that polls input, runs a tween or reads a singleton has to be told when the page opens, or it runs the whole time behind a closed screen — that is `MenuScreenPart` (`Menus/MenuScreenPart.cs`), which finds the page above it, starts disabled and enables itself off `MenuScreen.Opened` / `Closed` (`Reborn`, the two end-screen displays). Never gate one of these by switching a GameObject off; a part that wants to reveal itself later fades a `CanvasGroup` it owns, and `Reborn` will not take an Enter until something has `Arm()`ed it. Openings also play the page's own `StudioEventEmitter` if it has one — `MenuScreen`'s `openSound`, empty by default, which falls back to an emitter on the page itself. A step is **sequential, never a crossfade**: `MenuScreen.Step(from, to)` fades the outgoing page all the way out, plays the step sound, and only then brings the next one in. Every page records the one that opened it in `OpenedFrom`, so `MenuScreen.StepBack` returns there without a target of its own; a `MoveToAnotherCanvas` with an empty *to* is a back button. So "is a menu up" has exactly one answer, and something that merely happens to be active — the scene fade-in, the quit fader — can't darken the screen behind nothing.

**One `ScreenTint` under every screen, and the HUD goes with it.** The screens share a single tint image, wired into `ScreenTint` (`Menus/ScreenTint.cs`) on the object that parents them — no screen owns a dim layer or a hide-list of its own. A screen *holds* the tint while it is up, and the tint fades to whatever the **last** screen to ask for it wants, so stepping from one page to the next slides straight to the new level instead of dipping to nothing in between. The image's authored alpha is the darkest it ever gets — a screen's opacity is a fraction of it, listed per screen on `ScreenTint` (anything left out uses the default) — and the `Image` component is switched off entirely whenever the tint reaches nothing. What fades is a `CanvasGroup` over the image, never the image's own colour (see **Never fade an authored value in place** under Code style). `ScreenTint`'s `hiddenBehindMenus` is likewise the one list of what a menu covers — crosshair, bars, tips — faded with the tint, so the HUD leaves as the screen darkens and stepping between pages never flashes it back for a frame. A new HUD canvas is registered there rather than hiding itself; don't list a group whose alpha another system owns, since these are forced to full whenever no page is up. Each listed group's `Canvas` goes off once it has faded and **comes back the way it was found**, not switched on.

**One settings screen serves every menu.** `SettingsScreen` (`Menus/SettingsScreen.cs`) sits on the settings Canvas, is found by `SettingsScreen.Instance` rather than referenced, binds `Camera.main` itself and writes + applies the settings off `MenuScreen.Closed` — so the same prefab works dropped into any scene with no per-scene wiring. `OpenSettingsScreen` is the button that opens it from whatever page it lives on, resolving that page on first press rather than in `Awake` (the singleton-ordering rule above: `Pause` builds its own page during `Awake`), and Escape backs out of the settings before it unpauses. Settings that apply live do so through the singletons as the slider moves (`ComfortSettings`, `VolumeSettingLoader`); the framerate limit and mouse sensitivity are re-applied when the page closes.

**One gate for the clock, one lock for the controls.** Whether pausing is allowed is one question with one answer, the static `PauseGate`: anything that owns the screen or the clock — a choice menu while it is asking, the death screen, the win screen, the closed-portal failure, a scene change in flight — calls `PauseGate.Block(this)` and releases it after, and `Pause` (`Menus/Pause.cs`), which owns the clock and the menu page and nothing else, simply refuses to open while `PauseGate.Blocked`. Taking the controls away is likewise one thing, the static `PlayerControlLock`: callers `Set(owner, true/false)` and never disable `PlayerMovement`/`Attack`/the cursor directly, the set of owners is counted so overlapping holders can't unlock each other, and it drives movement, attack, dash, spell selection, mouselook (restoring sensitivity from PlayerPrefs on release) and the cursor. Neither survives a restart: `PlayerControlLock` clears on `sceneLoaded`, `PauseGate` prunes blockers as they are destroyed, and both reset at `SubsystemRegistration`.

**Player** (`Scripts/Player/`): CharacterController-based FPS movement in `Movement/` (`PlayerMovement`, `Bhop`, `Dash`, `DynamicFOV`, `CameraBob`, `FootstepSystem`). Combat in `Attack/`: `Attack` (singleton) implements hold-to-cast with a casting-progress slider, spells are `Bullet` prefabs picked by `selectedSpell`, mana is `Ammo`. Every spell identity — the pickup, the bullet, the pools, the cast VFX, the inventory slot — is the shared `SpellId` enum (`Scripts/Player/Attack/SpellId.cs`); the per-spell arrays stay index-based and are subscripted with a single `(int)spell` cast at the boundary, so enum order and array order must match. Vitals are `PlayerHP`, `PlayerStamina`, `Ammo`; progression is `PlayerEXP`, `UnlockedSpells`, `SpellSelector`. A separate "angel" healing mechanic lives in `AngelMind`/`AngelHeal`/`AngelHealingMinigame`. Angels can be killed, and a dead one is out of the system for good: `AngelMind.IsDead` derives from the angel's own `AiHealth` (no second flag), `AngelSpawner` never picks it or counts it as the angel you still owe a heal, `SetActive` refuses to wake it, and dying drops the `AngelPointerHelper`/`HelperSpirit` guidance if it was the one being led to — with every angel dead the spawner simply does nothing. Healing an angel costs 7 mana/s (then 10 HP/s once dry, floored at 10 HP) and ends with `AngelWishMenu` — three randomized upgrade wishes picked with 1/2/3 while movement, attacking and the inventory are disabled. Healing no longer refills the three bars automatically; a full restore is one of the wishes. Buffs that would otherwise have to be written into a prefab (spell damage, cast time, recoil, rocket-jump force, enemy speed) live in the static `WishUpgrades` and are read at the point of use — **never write an upgrade into a prefab field at runtime**, the Editor persists that between sessions.

**Spell inventory bar.** The HUD bar is modular: `SpellInventoryBar` (`UI/HUD/`) clones one disabled `SpellInventorySlot` template per spell at startup and owns the whole row — no hand-wired per-slot arrays. What it shows is *availability*, aggregated by the static `SpellAvailability`: a spell's slot appears when the spell is owned (`UnlockedSpells`), a pickup for it lies on the map (`SpellPickable.OnEnable`/`OnDisable` keep the counts, so pooling stays balanced), or the class grants it (Sanctus' light, Umbral's locked spell). Obtainable-but-not-owned slots keep the spell icon visible under the locked-tint overlay; when the set changes the row re-centres itself with a tween. Everything toggles at component level (`CanvasGroup` alpha for slots, `Image.enabled` for tint and badges) — slot GameObjects stay active for the whole run. A slot re-resolves any part wired from outside its own hierarchy to the same-named child, so template clones can't end up sharing one scene icon. Each slot owns its feedback badges as children (lock flash, unlock light, selection aura) — they clone with the slot, play in place at their editor-authored scales and follow it through re-layouts; only the selected-slot indicator stays bar-level, a child of the slots' parent. Digit keys map to *visible slot positions*, not SpellIds — `SpellSelector` asks the bar which spell sits under a digit and gives locked feedback through `SpellInventoryBar.Deny`. `UnlockedSpells` itself is pure state: the unlock flags, the duplicate-pickup mana refund, and the `Unlocked` event the bar plays its light-sweep/icon-reveal off.

**Player classes.** The *first* healed angel opens `PlayerClassMenu` before the wish menu — three of six classes drawn at random, picked with 1/2/3, or 4 to refuse; either way it only ever asks once per run, then hands straight over to `AngelWishMenu`. The choice lives in the static `PlayerClasses` (same split as `WishUpgrades`: one-off stat changes go onto the scene singletons when the class is taken, everything prefab-shaped is read at the point of use). The classes are Vesper (no health bar — magicka is doubled and *is* the health pool), Lightfoot (the only class with speed-damage, dash ×3, half health, angels cost double), Umbral (one shared black bar — health, magicka *and* stamina, which spends it only down to the 20% low-magicka line and is winded below that, at half fatigability — no spell inventory, a single spell whose splash needs the bar over half), Blastfool (rocket jumps ×4 force / ×2 self-damage, on the same distance falloff every class gets; damage ×0.2 grounded / ×0.7 airborne / ×2 mid rocket-jump, recoil ×0.1), Bastion (double health, piercing shots that hit ×2, ×1.5 spell cooldown, −20% speed, −20% jump) and Sanctus (the light spell converts enemies into allies via `ConvertedAlly` and commands them where it lands; own spells at 25%). **Speed-damage is Lightfoot-only** — for everyone else, and before a class is taken, spells land flat and `SpeedIndicator` is hidden. All the HUD reshuffling is in one place, `PlayerClassHud` (bar roots plus the heart/boot/palm icons, each tinted the colour of the bar its resource currently lives in). All three angel menus are the same menu asking different questions and share the abstract `AngelChoiceMenu` — canvas fade, numbered lines, digit keys, control lock-out through `PlayerControlLock` — so a subclass only supplies `SlotCount`, `RollOptions`, `BuildLine` and `OnChosen`. A line can also be *refused* rather than taken: `CanChoose` vetoes it, `AngelChoiceUi.Deny` flashes and shakes it, the base plays `deniedSound`, and `OnDenied` lets the menu fade a reason in via `ShowDenialNote` — which uses `AngelChoiceUi.noteText` if one is wired and otherwise borrows the first option line the open menu is not using, so it needs no extra wiring. The menu stays open throughout.

**Class upgrade levels.** Every *third* angel healed after the first (heals 3, 6, 9) opens `ClassUpgradeMenu` before the wish menu: one offer — the next level of the class you carry — or line 2 to refuse. A level asks for `level × 1000` EXP as a *threshold*, not a payment (nothing is deducted, and `PlayerEXP.playerLevel` is that same 1000-per-level line). **The offer never mentions EXP up front** — pick it without enough and the line flashes red, shakes, plays the refusal sound and only then does the note fade in with what the rite asks, what you carry and how much is short. A refusal does *not* close the menu: line 2 is the only way out, and the level comes round again three angels later. The ladder is `ClassUpgrades` (level, angels-healed count, EXP gate, the `LevelChanged` event and the `OnEnemyKilled`/`OnSpellHit` hooks that kill-and-hit upgrades hang off), and each class's three levels live in their own file under `Scripts/Player/Progression/ClassUpgrades/` — `VesperUpgrades`, `LightfootUpgrades`, `UmbralUpgrades`, `BlastfoolUpgrades`, `BastionUpgrades`, `SanctusUpgrades`, plus `WandererUpgrades` for a run where the class was refused. **Level 0 is the class exactly as it was before upgrades existed** — every default in those scripts is the number `PlayerClasses` used to hold as a constant, a level only ever adds to it, and `ClassUpgrades` resets the whole set at `SubsystemRegistration` as well as in the menu's `Awake`, so a previous run's level cannot leak into a fresh one through a static. Same split as everything else: stat changes go onto the scene singletons or `WishUpgrades` when the level is taken, anything prefab-shaped is a property on the class's own upgrade script read at the point of use (`UmbralUpgrades.ChargedBarThreshold`, `BlastfoolUpgrades.GroundedDamage`/`AirborneDamage`, `BastionUpgrades.SpellCooldownMultiplier`, `SanctusUpgrades.OwnDamageMultiplier`/`AllyStrikeMultiplier`/`MaxAllies`, `LightfootUpgrades.DashDamage`) — `PlayerClasses` now reads those defaults instead of holding its own constants. Each level earned lights one more ring on the hand: `ClassUpgradeRings` (rings wired in the Inspector, each posed where it belongs on its finger) fades one in and slides it down the finger into place.

**Input**: the new Input System via `InputActionReference` fields; subscribe to `.action.performed/.canceled` in `OnEnable` and unsubscribe in `OnDisable`. Active Input Handling is "Input System Package" only — never call legacy `UnityEngine.Input`; for one-off KeyCode-style polling (cheats, debug keys) use the `InputCompat` static bridge (`Scripts/Misc/InputCompat.cs`).

**Logging**: never call `Debug.Log*` directly — go through `DevLog.Info/Warn/Error` (`Scripts/Misc/DevLog.cs`). Its methods are `[Conditional("UNITY_EDITOR")]`/`[Conditional("DEVELOPMENT_BUILD")]`.

**Audio**: all sound goes through FMOD (`StudioEventEmitter`, `EventReference`) — do not use Unity `AudioSource` for new sounds. Changing audio content requires editing the FMOD Studio project and rebuilding banks.

## Code style

**No comments in code. None.** 
The one exception is `[Tooltip]` on a serialized field — that is Inspector text for whoever is wiring the prefab, not a comment.

**Never fade an authored value in place.** A component that writes its live value into the field holding its setting loses that setting the first time the Editor saves a play-mode state — which is exactly how `ScreenTint`'s image once ended up authored at alpha 0. Fade a `CanvasGroup` over the thing instead, and treat every authored colour, alpha or scale the same way (the sibling of "never write an upgrade into a prefab field at runtime").

**Resolve it once, at startup — cache everything.** Nothing that runs per frame or per FSM tick may allocate or go looking for something. All of allocation belongs in `Awake` or `Start`, stored in a field.

In code that ticks: reuse a preallocated buffer instead of building one — resolve it the first time and never look it up again.

**Optimal Math Calculations**
When building calculations, go from the lowest number or variable type, to biggest (Example - from bool, to int to float to Vectors).
Use multiplication instead of division where applicable.

## Gameplay reference

Controls: LMB shoot, RMB heal, WASD move, C stealth, Shift sprint, Space jump, 1/2/3 select spell (and pick a wish while the angel's wish menu is open). Cheats: ↑+3 unlocks the third spell, ↑+M refills magicka, typing a class name (`vesper`, `lightfoot`, `umbral`, `blastfool`, `bastion`, `sanctus`) takes that class — `PlayerClassCheat` goes through `PlayerClassMenu.Take`, so it grants exactly what the angel would, and it stays enabled so you can keep switching. Space+1/2/3 takes that class-upgrade level outright (EXP gate ignored), Space+L opens the upgrade menu and Space+P grants 1000 EXP — one level's worth, for testing the gate and the refusal note — `ClassUpgradeCheat`, which like `PlayerClassCheat` bootstraps its own hidden host object and needs no scene wiring. Cheat/debug scripts all live in `Test/` (`Test/Cheats/`, `Test/GameSpeedSlider`, `Test/DebugTestCameraShake`, plus `Test/CheatActivatedFeedback` for the on-screen toast) and are wrapped in `#if UNITY_EDITOR || DEVELOPMENT_BUILD` — their class shells stay so scene references survive, but the bodies compile only in Editor and development builds. Each one logs what it offers when it becomes usable, so the Console lists the available cheats on play.
